# DESIGN DECISIONS

تصمیم‌های طراحی به‌صورت ADR کوتاه. هر تصمیم: زمینه، تصمیم، دلیل، پیامد، و الزام مرتبط.

## ADR-001 — زبان پیاده‌سازی: Python 3.11+

**زمینه.** `SPEC §2` هدف را به C/C++ محدود می‌کند اما صریحاً می‌گوید این محدودیت به زبان
پیاده‌سازی خودِ ابزار مربوط نمی‌شود. `PROMPT §3` زبان پیشنهادی را Python 3 اعلام کرده است.

**تصمیم.** Python 3.11+، فقط با `PyYAML` و `jsonschema` به‌عنوان وابستگی اجباری.

**دلیل.** parse خروجی sanitizer، مدیریت process، و تولید گزارش در Python هزینهٔ توسعهٔ بسیار
کمتری دارد؛ بخش حساس به کارایی (اجرای باینری) به هر حال در زیرپروسه است.

**پیامد.** وابستگی به مفسر Python در محیط CI — با Dockerfile پوشش داده می‌شود.
`R-SCOPE-04`

## ADR-002 — ایزوله‌سازی با bubblewrap، نه Docker-per-test

**زمینه.** اصلاحیهٔ معماری در `PROMPT` صریح است: یک container به ازای هر CI job، یک sandbox
سبک به ازای هر اجرای تست؛ ابزار نباید container بسازد.

**تصمیم.** `BubblewrapSandboxBackend` به‌عنوان backend پیش‌فرض و تنها backend ایزولهٔ واقعی.
هیچ فراخوانی Docker API/socket در کد ابزار وجود ندارد.

**دلیل.** ساخت container به ازای هر تست ده‌ها برابر کندتر است و نیازمند دسترسی به daemon
(یک سطح دسترسی خطرناک داخل CI). bubblewrap با user namespace بدون root کار می‌کند.

**پیامد.** نیاز به پشتیبانی user namespace در runner. `doctor` این قابلیت را پیش از اجرا probe
می‌کند و در نبودش exit 30 می‌دهد، نه اجرای ناامن.
`R-SBX-01/02/03/06/07`

## ADR-003 — backend ناامن `subprocess` فقط با opt-in صریح

**زمینه.** برخی محیط‌ها (مثلاً container بدون `CAP_SYS_ADMIN` و بدون userns) bubblewrap را
اجازه نمی‌دهند.

**تصمیم.** یک backend `subprocess` وجود دارد که **فقط** با `--i-accept-unsafe-execution` در CLI
یا `sandbox.backend: subprocess` به‌همراه `sandbox.unsafe_ack: true` فعال می‌شود، و در این حالت
در گزارش `sandbox_backend: subprocess` و یک هشدار صریح ثبت می‌گردد.

**دلیل.** `R-SBX-07` می‌گوید هیچ تست آسیب‌پذیری بدون ایزوله‌سازی اجرا نشود؛ اما قابلیت توسعه
و دیباگ محلی نیاز به مسیر فرار دارد. ساختن آن به‌صورت صریح و قابل‌مشاهده در گزارش، تفاوت میان
«راه فرار مستند» و «ناامنی پنهان» است.

**پیامد.** در CI هرگز فعال نمی‌شود؛ workflow آن را تنظیم نمی‌کند.
`R-SBX-07`

## ADR-004 — ترتیب اولویت exit code از سند رسمی

**زمینه.** تعارض C-01 در `docs/REQUIREMENTS.md`.

**تصمیم.** `EXIT_PRECEDENCE = (30, 10, 20, 40, 0)`.

**دلیل.** قانون صفر: سند رسمی درس مرجع است. منطق آن هم دفاع‌پذیر است — اگر build یا پیکربندی
خراب باشد، هیچ ادعای امنیتی دیگری معتبر نیست، پس باید بالاترین اولویت را داشته باشد.

**پیامد.** ترتیب در یک ثابت واحد متمرکز است و تغییر آن یک‌خطی است.
`R-EXIT-06`

## ADR-005 — Crash signature مبتنی بر نوع خطا + فریم‌های نرمال‌شده

**زمینه.** کوچک‌سازی ورودی و تشخیص «همان خطا» به یک معیار پایدار نیاز دارد. exit code غیرصفر
معیار نیست (`R-REPRO-07`).

**تصمیم.** `signature = sha256(error_type | detection_mechanism | norm(frame_0..frame_{N-1}))`
که `N=3` پیش‌فرض و `norm` آدرس‌های مطلق، offsetها، و مسیرهای مطلق را حذف می‌کند و فقط
`module!function+file:line` نرمال‌شده را نگه می‌دارد. اگر symbolization در دسترس نباشد، فریم‌ها
با `module+relative_offset` نرمال می‌شوند و `signature_quality = "unsymbolized"` ثبت می‌شود.

**دلیل.** پایداری در برابر ASLR و تغییر مسیر build، و حساسیت به تغییر محل واقعی خطا.

**پیامد.** تغییر کامپایلر یا سطح بهینه‌سازی می‌تواند inline شدن توابع و در نتیجه تغییر signature
را موجب شود. مقایسهٔ signature فقط میان buildهای متناظر (هم‌mode) انجام می‌شود.
`R-DYN-12`, `R-REPRO-06`

## ADR-006 — Oracle مستقل و commit‌شده پیش از ارزیابی

**زمینه.** `SPEC §2 p2`: خروجی نسخهٔ وصله‌شده مرجع صحت نیست.

**تصمیم.** Oracle برای هر هدف در `targets/<name>/SPECIFICATION.md` (توضیح انسانی) و در
بخش `oracle` هر test case در YAML (قابل اجرا) تعریف می‌شود. هیچ مسیر کدی برای تولید خودکار
oracle از اجرای باینری وجود ندارد. هر oracle فیلد `source` دارد: `specification` /
`upstream_docs` / `reference_test_suite` / `instructor_approved`.

**دلیل.** تنها راه دفاع‌پذیر برای ادعای «پسرفت عملکردی» این است که معیار صحت پیش از دیدن
نتیجهٔ وصله تثبیت شده باشد.

**پیامد.** برای هدف واقعی، oracle باید از مستندات بالادست استخراج شود که کار دستی دارد؛
تست‌های بدون oracle فقط در محور امنیت شرکت می‌کنند و در محور کامل‌بودن `missing_oracle`
ثبت می‌شود.
`R-ORC-01..05`

## ADR-007 — همبستگی با diff: امتیازدهی چندسطحی به‌جای تصمیم دودویی

**زمینه.** `SPEC §3.1`: همجواری ظاهری کافی نیست؛ ارتباط غیرمستقیم باید در نظر گرفته شود؛
نبود شواهد ⇒ `UNKNOWN`.

**تصمیم.** چهار سطح:

| سطح | شرط |
|---|---|
| `CONFIRMED` | فریمی از stack trace در فایلِ تغییرکرده **و** داخل تابعی که hunk آن را لمس کرده **و** فاصلهٔ خطی ≤ محدودهٔ hunk |
| `LIKELY` | فریمی در تابع تغییرکرده ولی خارج از خطوط دقیق hunk، یا caller مستقیم یک تابع تغییرکرده |
| `WEAK` | فقط فایل مشترک است (همجواری سطح فایل) یا فاصلهٔ خطی زیاد |
| `UNKNOWN` | stack trace نداریم، یا هیچ اشتراکی یافت نشد |

تصمیم نهایی `NEW_ISSUE` فقط با `CONFIRMED` یا `LIKELY` به «تأییدشده» ارتقا می‌یابد؛ `WEAK` و
`UNKNOWN` به محور کامل‌بودن می‌روند و در گزارش با همان برچسب باقی می‌مانند.

**دلیل.** مستقیماً از متن `SPEC` می‌آید و از ادعای اضافی جلوگیری می‌کند.

**پیامد.** ممکن است یافتهٔ واقعی مرتبط با وصله، در نبود symbolization، `WEAK` بماند؛ این یک
false-negative آگاهانه و مستند است (`docs/LIMITATIONS.md`).
`R-CORE-04/05/06/07`

## ADR-008 — ماتریس اجرای چهارتایی و ممنوعیت اختلاط build modeها

**زمینه.** `SPEC §3.2`: نتیجهٔ release نباید با sanitized مخلوط شود؛ مقایسهٔ قبل/بعد باید در
buildهای متناظر باشد.

**تصمیم.** کلید هر نتیجه `(test_id, version, build_mode)` است و تابع مقایسه فقط جفت‌هایی با
`build_mode` یکسان را می‌پذیرد (در کد با `assert` و در تست واحد تضمین می‌شود).
محور عملکرد از `release` به‌عنوان مرجع استفاده می‌کند و نتیجهٔ `sanitized` را به‌صورت
اطلاعاتی ثبت می‌کند، چون ASan رفتار خروجی و زمان‌بندی را تغییر می‌دهد.

**دلیل.** جلوگیری از نتیجه‌گیری نادرست ناشی از تفاوت ابزارگذاری.

**پیامد.** هزینهٔ اجرا دو برابر می‌شود — قابل قبول در مقیاس این پروژه.
`R-DYN-03/08/09`, `R-CORE-09`

## ADR-009 — ddmin بایت‌محور با predicate مبتنی بر signature

**زمینه.** هدف‌ها ورودی باینری یا متنی دارند؛ یک الگوریتم عمومی لازم است.

**تصمیم.** پیاده‌سازی `ddmin` کلاسیک روی آرایهٔ بایت با granularity دوبرابرشونده، به‌همراه
بودجهٔ سخت (`max_iterations`, `budget_seconds`) و cache نتایج بر اساس هش ورودی.
predicate: «اجرای کوچک‌شده همان `crash_signature` را تولید کند».

**دلیل.** عمومی‌بودن (مستقل از فرمت)، و انطباق مستقیم با `R-REPRO-06/07`.

**پیامد.** برای فرمت‌های دارای checksum، کاهش محدود می‌شود. این محدودیت مستند است و
درصد کاهش واقعی در گزارش ثبت می‌شود، نه ادعای کاهش.
`R-REPRO-05..09`

## ADR-010 — دو هدف: toy ساخته‌شده + پروژهٔ واقعی open-source

**زمینه.** `SPEC §4` دو برنامهٔ مستقل می‌خواهد که حداقل یکی واقعی باشد.

**تصمیم.** هدف اول: `recparse`، یک record parser باینری نوشته‌شده به C با یک stack buffer
overflow واقعی ناشی از اعتبارسنجی نادرست طول، در چهار نسخه (base / correct / incomplete /
regression). هدف دوم: یک کتابخانهٔ C واقعی با CVE و commit رفع واقعی در تاریخچهٔ بالادست.

**دلیل.** toy تضمین می‌کند هر چهار سناریوی ارزیابی به‌صورت قطعی و تکرارپذیر پوشش داده شوند؛
هدف واقعی قابلیت تعمیم را اثبات می‌کند.

**پیامد.** هدف واقعی به دریافت منبع از شبکه نیاز دارد؛ مسیر منبع و revision دقیق در config ثبت
می‌شوند و اسکریپت آماده‌سازی جداگانه است تا اجرای آفلاین toy ممکن بماند.
`R-SCOPE-05/06`, `ADR-011`

## ADR-011 — مخزن هدف toy به‌صورت قابل بازتولید ساخته می‌شود

**زمینه.** ابزار روی «دو revision یک مخزن git» کار می‌کند، اما قرار دادن یک مخزن git تودرتو
داخل مخزن تحویلی باعث gitlink بدون submodule و تحویل شکسته می‌شود.

**تصمیم.** درخت منبع هر چهار نسخه در `targets/recparse/versions/<name>/` commit می‌شود،
به‌همراه `targets/recparse/patches/*.patch` (diff واقعی نسبت به base). اسکریپت
`targets/recparse/bootstrap.sh` با author/date ثابت یک مخزن git واقعی در
`targets/recparse/repo/` می‌سازد: شاخهٔ `base` و سه شاخهٔ وصله. این پوشه در `.gitignore` است.

**دلیل.** commit و diff کاملاً واقعی‌اند (ابزار `git diff` واقعی می‌خواند)، تحویل تمیز می‌ماند، و
هش‌ها به‌خاطر تاریخ ثابت بین اجراها یکسان‌اند.

**پیامد.** پیش از اولین اجرا باید `make bootstrap` یا اسکریپت را اجرا کرد؛ در CI یک گام جداگانه
است و در `README` مستند می‌شود.
`R-SCOPE-03`, `R-DEL-01`

## ADR-012 — «خطای پایه بازتولید نشد» ⇒ INCONCLUSIVE، نه PASS

**زمینه.** `SPEC §3.5`: شرط PASS شامل «خطای هدف روی نسخهٔ پایه بازتولید شده» است.

**تصمیم.** شرط `base_vulnerability_reproduced` از شواهد محاسبه می‌شود (وجود ≥۱ security event
روی هر تستی روی base)، نه از برچسب‌گذاری دستی test caseها. اگر برقرار نباشد، نتیجه ۴۰ است.

**دلیل.** هم الزام `SPEC` را برآورده می‌کند و هم برای وصله‌های دیده‌نشده (`R-SCOPE-09`) کاملاً
عمومی می‌ماند، چون به هیچ فراداده‌ای دربارهٔ وصله وابسته نیست.

**پیامد.** اگر کاربر مجموعه تستی بدهد که هیچ‌کدام روی base خطا تولید نمی‌کنند، ابزار PASS
نمی‌دهد — این رفتار عمدی و مستند است.
`R-EXIT-01/05`, `R-SCOPE-09`

## ADR-013 — تفکیک سه محور تا آخرین مرحله

**زمینه.** `SPEC §3.5`: «تمام یافته‌ها و وضعیت‌های مستقل امنیت، عملکرد و تکمیل تحلیل … در JSON
باقی بمانند».

**تصمیم.** `Classification` سه فیلد مستقل `security_status`، `functional_status`،
`completeness_status` دارد و `final_classification` + `exit_code` از آن‌ها مشتق می‌شود. هیچ
محوری محور دیگر را بازنویسی نمی‌کند.

**دلیل.** گزارش باید برای توسعه‌دهنده قابل تفسیر بماند حتی وقتی exit code یک عدد است.

**پیامد.** مصرف‌کنندهٔ JSON می‌تواند سیاست خودش را روی سه محور اعمال کند.
`R-EXIT-07`
