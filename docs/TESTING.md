# TESTING

مجموعه آزمون **خود ابزار** — نه آزمون‌های برنامه‌های هدف.

```bash
pytest -q                     # همه
pytest -q -m "not slow"       # سریع، بدون اجراهای سرتاسری
pytest -q -m sandbox          # فقط تأیید ایزوله‌سازی
pytest -q --no-header -v      # با نام هر تست
```

## نشانه‌ها (markers)

| نشانه | نیازمندی | در نبودش |
|--------|-----------|-----------|
| `sandbox` | `bwrap` قابل اجرا | skip با دلیل |
| `toolchain` | `gcc` و `cmake` | skip با دلیل |
| `slow` | مخزن هدف ساخته‌شده | skip با راهنمای `bootstrap.sh` |

skip کردن با پیام صریح انجام می‌شود، نه با pass دروغین.

## فایل‌ها

### `test_crash_analysis.py` — ۲۷ تست

طبقه‌بندی خطا از خروجی **واقعی** sanitizer (کپی‌شده از اجرای همین پروژه)، و مرزهایی که
محور امنیت را سالم نگه می‌دارند:

- کد خروج غیرصفر به‌تنهایی کرش نیست
- timeout بر گزارش ناقص ASan اولویت دارد
- `SIGXCPU`/`SIGXFSZ` محدودیت منابع‌اند، نه خطای امنیتی
- `SIGKILL` بدون تشخیص، علت را «اثبات‌نشده» اعلام می‌کند
- سیگنال استنتاجی `confidence` را کاهش می‌دهد و دلیلش را می‌نویسد

و رفتار امضاها:

- جابه‌جایی شماره‌خط فقط امضای دقیق را عوض می‌کند، نه امضای مکان
- مسیر فراخوانی متفاوت ⇒ امضای مکان متفاوت
- فریم‌های بدون نماد با `unsymbolized` علامت می‌خورند

### `test_differential_and_classification.py` — ۴۳ تست

هر خانهٔ هر دو جدول تصمیم، به‌علاوهٔ موتور طبقه‌بندی:

- شش حالت محور امنیت
- شش حالت محور عملکرد، شامل «هر دو نقض می‌کنند» که **نباید** پسرفت اعلام شود
- رد کردن ساختاری جفت‌های با build mode متفاوت
- هر پنج کد خروج و ۱۴ حالت اولویت
- یک تست ترکیبی که **همهٔ** ترکیب‌های (امنیت × عملکرد × بازتولید پایه × ایزوله‌سازی)
  را می‌پیماید و تأیید می‌کند هیچ ترکیبی به کد تعریف‌نشده نمی‌افتد

### `test_sandbox.py` — ۱۹ تست

یک تست به ازای هر بند فهرست تأیید اصلاحیهٔ معماری:

| بند | تست |
|-----|-----|
| دسترسی خارج از sandbox مسدود | `/home` نامرئی، فایل مخفی خارج غیرقابل خواندن، `/etc/shadow` غیرقابل دسترس |
| محدود بودن دسترسی شبکه | `getent hosts` شکست می‌خورد |
| اعمال Timeout | `sleep 60` با بودجهٔ ۲ ثانیه کشته می‌شود |
| اعمال محدودیت منابع | fork bomb مهار می‌شود، خروجی سقف می‌خورد، فضای آدرس محدود می‌شود |
| پاک‌سازی Process پس از تست | هیچ `sleep` بازمانده‌ای وجود ندارد |
| اجرای مستقل تست‌های متوالی | فایل نوشته‌شده در `/tmp` اجرای بعدی را آلوده نمی‌کند |
| حفظ شواهد پس از حذف sandbox | stdout/stderr پس از `rmtree` همچنان در دست‌اند |
| باینری فقط-خواندنی | نوشتن روی باینری هدف شکست می‌خورد |
| جدول پراسس خصوصی | کمتر از ۱۵ پراسس دیده می‌شود |
| انتخاب backend | backend بدون ایزوله‌سازی بدون تأیید صریح رد می‌شود |

### `test_patch_analysis.py` — ۱۸ تست

- تجزیهٔ diff: تغییر، درج خالص، حذف خالص، فایل افزوده/حذف‌شده، چندفایلی
- **نقطهٔ درج**: وصلهٔ صرفاً افزایشی باید سمت قدیم را هم علامت بزند
- جست‌وجوی فایل با نام، و رد کردن نام مبهم
- نگاشت خط به تابع در برابر: ماکروی تابع‌مانند، آغازگر struct، امضای چندخطی، آکولاد
  داخل رشته و توضیح

### `test_config_and_minimize.py` — ۳۱ تست

- مسیرهای رد پیکربندی: کلید ناشناخته، نبود build release، مخزن غیر git، شناسهٔ تکراری،
  قالب ناشناخته، قالب ورودی جاافتاده، backend ناامن بدون تأیید، کمتر از ۳ بازپخش
- قالب‌گذاری: بسط پرچم‌ها، حفظ مسیرِ دارای فاصله، حذف آرگومان خالی
- تطبیق‌گرهای Oracle و رفتار «بدون Oracle = NOT_APPLICABLE»
- ویژگی‌های ddmin: رسیدن به نشانگر دقیق، عدم کاهش بیش از حد، رعایت بودجه، cache

### `test_end_to_end.py` — ۲۶ تست

هر سه سناریو از طریق **CLI واقعی** روی ماتریس چهارتایی واقعی، و سپس بررسی شواهد:

- کدهای خروج ۰، ۱۰، ۲۰
- بازتولید خطای پایه پیش از ادعای `PASS`
- همبستگی `CONFIRMED` غیرمستقیم برای مسیر مسدودشده و `WEAK` برای مسیر باقی‌مانده
- **هر `evidence_ref` به فایلی اشاره می‌کند که واقعاً وجود دارد**
- نتایج release و sanitized هرگز مخلوط نمی‌شوند
- build سانیتایزشده چیزی را آشکار کرده که release نکرده
- بسته‌ها ≥۳ بار بازپخش شده‌اند و `REPRODUCE.md` دارند
- تست‌های رگرسیون هر سه انتظار را دارند
- خلاصهٔ markdown با JSON نمی‌خواند
- **اجرای شکست‌خورده همچنان گزارش معتبر تولید می‌کند**
- سناریوی وصلهٔ دیده‌نشده، و بررسی ساختاری اینکه هیچ فیلدی در ورودی موتور طبقه‌بندی
  نام revision یا وصله ندارد

## دو تستی که آسان از دست می‌روند

```python
def test_every_finding_references_evidence_that_exists(...)

```

اولی تضمین می‌کند هیچ ادعایی بدون شاهد روی دیسک نیست. دومی ویژگی «وصلهٔ دیده‌نشده» را
به‌صورت **ساختاری** بررسی می‌کند، نه با امید.

## وقتی تست و ابزار اختلاف دارند

دو بار در طول توسعه پیش آمد و هر دو آموزنده بود:

1. تستی فرض کرده بود segfault روی نسخهٔ وصله‌شده **یک** یافته تولید می‌کند. ابزار درست
   بود: هم `NEW_ISSUE` است و هم `FUNCTIONAL_REGRESSION`. تست اصلاح شد.
2. تستی اصرار داشت مسیری که فاصله دارد باید یک آرگومان بماند. تست درست بود و قانون
   بسط قالب در ابزار بیش‌ازحد عمومی بود. ابزار اصلاح شد.
