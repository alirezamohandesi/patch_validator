# DEFENSE GUIDE — راهنمای دفاع فردی

> سند رسمی می‌گوید دفاع **فردی و جداگانه** است و هر عضو باید بتواند معماری کلی، منطق بخش
> خودش، تفسیر شواهد، و یک **تغییر محدود در کد یا پیکربندی** را در زمان جلسه انجام دهد.
> بارم: ۳ نمره معماری + ۳ نمره تحلیل یک یافته + ۴ نمره اعمال تغییر، و دریافت **حداقل ۱
> نمره از هر سه محور** شرط لازم است.
>
> این سند برای هر عضو: دامنهٔ مسئولیت، توابع کلیدی، تصمیم‌های قابل دفاع، یک یافتهٔ واقعی
> برای تحلیل، و یک تمرین تغییر محدود با روش آزمایش آن.

---

## آنچه همهٔ اعضا باید بتوانند بگویند

هر چهار نفر باید این چهار چیز را بدون نگاه به کد توضیح دهند:

### ۱. چرا «برنامه کرش نکرد» کافی نیست

ابزار سه محور **مستقل** نگه می‌دارد تا آخرین لحظه:

| محور | پرسش |
|------|------|
| امنیت | آیا خطای حافظه‌ای روی نسخهٔ وصله‌شده مشاهده می‌شود؟ |
| عملکرد | آیا رفتار مورد انتظار روی ورودی‌های معتبر حفظ شده؟ |
| کامل‌بودن تحلیل | آیا همهٔ بررسی‌های الزامی واقعاً انجام شدند؟ |

فقط در آخرین مرحله این سه با اولویت `30 > 10 > 20 > 40 > 0` به یک کد خروج تبدیل می‌شوند،
و هر سه در JSON باقی می‌مانند.

### ۲. چرا `PASS` مشروط به بازتولید خطای پایه است

اگر هیچ خطایی روی نسخهٔ پایه دیده نشود، چیزی وجود ندارد که نشان دهد وصله آن را رفع کرده؛
نتیجه `INCONCLUSIVE` (۴۰) است نه `PASS`. این شرط از **شواهد** محاسبه می‌شود (وجود حداقل
یک `security_event` روی base) نه از برچسب‌گذاری دستی test caseها — و دقیقاً به همین دلیل
برای وصله‌های دیده‌نشدهٔ روز دفاع هم معتبر می‌ماند.

### ۳. چرا ماتریس چهارتایی است

`{base, patched} × {release, sanitized}`. نتایج دو build هرگز مخلوط نمی‌شوند؛ این قاعده
در `CasePair.__post_init__` با یک استثنا تضمین شده، نه با قرارداد.

**شاهد واقعی از همین پروژه:** ورودی `boundary_text32` روی release build با کد ۰ و بدون
هیچ نشانه‌ای خارج می‌شود، ولی روی sanitized build یک `STACK_BUFFER_OVERFLOW` قطعی تولید
می‌کند. اگر فقط release اجرا می‌شد، این نقص نامرئی بود.

### ۴. چرا ابزار بدون sandbox اجرا نمی‌کند

ما عمداً یک باینری آسیب‌پذیر را با ورودی مخرب اجرا می‌کنیم. نبود ایزوله‌سازی یک خطای
پیکربندی (کد ۳۰) است، نه دلیلی برای اجرای بدون محافظت.

## Member 1 — Architecture, Configuration, Build System, CLI

### دامنه
`src/patch_validator/config/` · `build/` · `vcs/` · `cli.py` · `artifacts.py` ·
`util/templating.py`

### توابع کلیدی

| تابع | چه می‌کند و چرا مهم است |
|------|------------------------|
| `config.loader.load_config` | YAML → اعتبارسنجی JSON Schema → مدل dataclass → بررسی‌های سازگاری که schema نمی‌تواند بیان کند |
| `util.templating.render_argv` | قالب‌ها را به argv تبدیل می‌کند؛ **هیچ shell‌ای درگیر نیست** |
| `build.manager.prepare_sources` | دو revision را به‌صورت `git worktree` کنار هم checkout می‌کند |
| `build.manager.build` | اجرای دستورهای ساخت، تأیید ELF بودن خروجی، ثبت کامل provenance |
| `cli._load` | اعمال `--patched-revision` روی پیکربندی |

### تصمیم‌های قابل دفاع

**چرا argv به‌جای رشتهٔ shell؟** مسیری که فاصله دارد نمی‌تواند شکل دستور را عوض کند و
تزریق shell ممکن نیست. رشته‌ها **پیش از** جایگذاری با قواعد POSIX تقسیم می‌شوند.

**چرا `str.format` استفاده نشد؟** پرچم‌های کامپایلر آکولاد دارند
(`-Wl,--defsym={sym}=1`). `format` یا `KeyError` می‌دهد یا بی‌صدا بازنویسی می‌کند. ما فقط
توکن‌های **شناخته‌شده** را جایگزین می‌کنیم و بقیه را دست‌نخورده می‌گذاریم.

**چرا فقط `cflags`/`ldflags` به چند آرگومان بسط می‌یابند؟** چون ذاتاً فهرست پرچم‌اند.
مسیرها هرگز تقسیم نمی‌شوند. این قانون یک بار اشتباه پیاده شد و تست
`test_a_path_with_spaces_stays_one_argument` آن را گرفت.

**چرا خطای ساخت یافته نیست؟** اگر build خراب باشد هیچ ادعای امنیتی مبتنی بر آن ارزشی
ندارد؛ به همین دلیل کد ۳۰ بالاترین اولویت را دارد.

### یافتهٔ واقعی برای تحلیل

`runs/<id>/builds/base.sanitized/meta.json` — توضیح بده هر فیلد چرا برای بازتولید لازم
است و اگر `binary_sha256` نبود چه چیزی از دست می‌رفت.

### تمرین تغییر محدود

> **افزودن یک سطح بهینه‌سازی سوم:** یک build mode جدید اضافه کن.

- انتظار: schema فقط `release` و `sanitized` را می‌پذیرد، پس هم `config/schema.py` و هم
  `BuildMode` باید تغییر کنند.
- **آزمایش:** `patch-validator check-config` باید بپذیرد، `build` باید سه باینری بسازد،
  و `pytest tests/test_config_and_minimize.py` باید سبز بماند.
- نکتهٔ دفاعی: چرا محور عملکرد همچنان باید `release` را مرجع بداند؟

> **جایگزین ساده‌تر:** یک placeholder جدید مثل `{target_name}` به `BUILD_PLACEHOLDERS`
> اضافه کن و در `BuildManager.build` مقداردهی کن. آزمایش: یک config که از آن استفاده
> می‌کند باید build شود، و یک placeholder ناشناخته باید همچنان خطای واضح بدهد.

## Member 2 — Dynamic Execution, Crash Analysis, Sanitizers, Sandbox

### دامنه
`src/patch_validator/execution/` · `sandbox/` · `analysis/crash.py` ·
`analysis/frames.py`

### توابع کلیدی

| تابع | چه می‌کند |
|------|-----------|
| `sandbox.bubblewrap.build_command` | ساخت خط فرمان bwrap: namespaceها، bindها، env |
| `sandbox.runner.execute` | نصب rlimitها پیش از `execve`، session مستقل، timeout، کشتن کل process group |
| `sandbox.base.decode_signal_exit` | بازیابی سیگنال از کد خروج `128+N` |
| `crash.CrashAnalyzer.analyze` | ترتیب تشخیص‌دهنده‌ها و مرزهای محور امنیت |
| `crash.CrashAnalyzer._signatures` | ساخت دو امضا: دقیق و مستقل از شمارهٔ خط |

### تصمیم‌های قابل دفاع

**چرا دو امضا؟** امضای دقیق (با شمارهٔ خط) برای کوچک‌سازی لازم است: «آیا هنوز همان
باگ در همان جاست؟». امضای مستقل از خط برای مقایسهٔ base با patched لازم است، چون وصله
شماره‌خط‌ها را جابه‌جا می‌کند و بدون آن هر خطای واقعاً یکسان، «جابه‌جاشده» گزارش می‌شد.

**چرا timeout اول بررسی می‌شود؟** اجرایی که وسط چاپ گزارش ASan کشته شده، گزارش ناقص
دارد. اگر اول دنبال ASan می‌گشتیم، یک timeout به خطای حافظه‌ای تأییدشده تبدیل می‌شد.

**چرا `RLIMIT_NPROC` داخل sandbox اعمال می‌شود؟** این محدودیت پراسس‌های **کل uid** را
می‌شمارد. اعمال از والد باعث شد bwrap با `EAGAIN` شکست بخورد چون کاربر CI از قبل
پراسس‌های زیادی داشت. داخل user namespace، uid نگاشت‌شده هیچ پراسسی ندارد.

**چرا `RLIMIT_AS` برای sanitized اعمال نمی‌شود؟** ASan چندین ترابایت فضای آدرس رزرو
می‌کند و با محدودیت، پیش از `main()` می‌میرد. به‌جای آن `hard_rss_limit_mb` خود ASan.

### یافتهٔ واقعی برای تحلیل

خروجی `exec/vuln_text_long/base.sanitized/stderr.bin`:

```
#0 copy_payload src/record.c:21
#1 handle_text  src/record.c:30
#2 parse_stream src/record.c:102
```

بگو چرا فریم‌های `memcpy` (دو فریم بالاتر) در `target_frames` نیستند، و چرا این برای
همبستگی با diff حیاتی است.

### تمرین تغییر محدود

> **تعداد فریم‌های امضا را از ۳ به ۲ کاهش بده** (`SIGNATURE_FRAMES` در `crash.py`).

- پیش‌بینی کن چه چیزی عوض می‌شود: دو خطا که در دو تابع فراخوان متفاوت رخ می‌دهند ولی سه
  فریم اولشان مشترک است، حالا یک امضا می‌گیرند.
- **آزمایش:** `pytest tests/test_crash_analysis.py -k signature`. تست
  `test_different_call_path_gives_a_different_location_signature` باید همچنان سبز بماند
  (چون `handle_text` و `handle_raw` در فریم ۱ هستند). سپس
  `patch-validator validate --patched-revision incomplete-patch` را اجرا کن و ببین آیا
  شمارش یافته‌ها عوض شد.

## Member 3 — Patch Correlation, Differential Testing, Classification

### دامنه
`src/patch_validator/analysis/diffparse.py` · `cfunctions.py` · `patch.py` ·
`differential.py` · `oracle.py` · `classify/`

### توابع کلیدی

| تابع | چه می‌کند |
|------|-----------|
| `diffparse.parse_patch` | تجزیهٔ unified diff، با تفکیک خطوط سمت قدیم و جدید |
| `cfunctions.extract_functions` | نگاشت خط → تابع با خنثی‌سازی رشته/توضیح و شمارش آکولاد |
| `patch.PatchAnalyzer._match_frame` | درجه‌بندی ارتباط یک فریم با diff |
| `differential.DifferentialTester.compare` | جدول‌های تصمیم دو محور |
| `classify.engine.classify` | ترکیب سه محور + ۹ بررسی الزامی → کد خروج |

### تصمیم‌های قابل دفاع

**چرا همبستگی چهار سطح دارد و نه بله/خیر؟** سند صریح است: «صرف همجواری ظاهری خطا و
Diff برای اثبات ارتباط کافی نیست» و «در صورت ناکافی بودن شواهد، ارتباط نامشخص گزارش
شود». `WEAK` یعنی فقط فایل مشترک است؛ این یافته را به وصله نسبت نمی‌دهیم.

**چرا «نقطهٔ درج» ثبت می‌شود؟** وصله‌ای که فقط خط اضافه می‌کند در سمت base هیچ خط
حذف‌شده‌ای ندارد، پس بدون این، خطای مشاهده‌شده روی base هرگز به آن وصله مرتبط نمی‌شد.
این باگ در عمل دیده شد: `incomplete-patch` ابتدا `WEAK` می‌داد و پس از اصلاح، `CONFIRMED`
غیرمستقیم شد.

**چرا پسرفت عملکردی نیاز به اثبات دوطرفه دارد؟** اگر base هم Oracle را نقض کرده باشد،
اختلاف دو نسخه ممکن است ربطی به وصله نداشته باشد. در آن حالت `INCONCLUSIVE` گزارش
می‌شود و هرگز به کد ۲۰ تبدیل نمی‌گردد.

### یافتهٔ واقعی برای تحلیل

**بهترین نمونه در کل پروژه** — خروجی `runs/cjson/report.json`:

```
FIXED  security_object_truncated_after_comma   corr=LIKELY  cJSON.c:parse_object()  indirect=True
  base: HEAP_BUFFER_OVERFLOW detected by address_sanitizer at cJSON.c:787
  why : the fault surfaced in parse_string at cJSON.c:787, which is reached
        from the changed code
```

خطا در `parse_string` رخ داده — تابعی که وصلهٔ واقعی بالادست **اصلاً دست نزده**. ابزار
با پیمایش فریم‌های بالاتر، `parse_object()` را پیدا کرده و ارتباط را **غیرمستقیم** علامت
زده. این دقیقاً همان «امکان ارتباط غیرمستقیم از طریق Caller» است که سند می‌خواهد، روی
یک CVE واقعی.

### تمرین تغییر محدود

> **سطح `WEAK` را به «منتسب به وصله» ارتقا بده** (در `Correlation.attributed`).

- پیش‌بینی: یافتهٔ `INCOMPLETE_FIX` مسیر RAW در `incomplete-patch` که الان `WEAK` است،
  به وصله نسبت داده می‌شود — در حالی‌که آن وصله هرگز آن مسیر را لمس نکرده.
- **آزمایش:** `pytest tests/test_end_to_end.py -k surviving_path` باید **بشکند**. توضیح
  بده چرا شکستن این تست نشانهٔ درستی طراحی اصلی است، نه نقص تست.

> **جایگزین:** یک جدول تصمیم جدید اضافه کن — وقتی base خطا دارد و patched خطای
> **متفاوتی** دارد، به‌جای `INCOMPLETE_FIX` با confidence متوسط، یک `NEW_ISSUE` جداگانه
> هم تولید کن. آزمایش: `tests/test_differential_and_classification.py::
> TestSecurityAxis::test_fault_that_moves_is_still_incomplete_but_less_certain`.

## Member 4 — Minimization, Reproduction, Regression, CI/CD, Reporting

### دامنه
`src/patch_validator/minimize/` · `reproducer/` · `regression/` · `report/` ·
`Dockerfile` · `.github/workflows/`

### توابع کلیدی

| تابع | چه می‌کند |
|------|-----------|
| `minimize.ddmin.Minimizer.minimize` | ddmin بایت‌محور با بودجه و cache |
| `reproducer.bundle.ReproducerManager.create` | ساخت بسته + ≥۳ بازپخش + تعیین پایداری |
| `regression.generator.RegressionGenerator.generate` | تولید تست با سه assertion |
| `report.writer.validate` | اعتبارسنجی گزارش با schema پیش از نوشتن |

### تصمیم‌های قابل دفاع

**چرا predicate بر اساس امضای خطاست و نه کد خروج؟** سند صریح است: «هر کد خروج غیرصفر
معیار حفظ خطا نیست». ورودی کوچک‌تری که جای دیگری کرش کند، یک باگ دیگر است و تست
رگرسیونِ ساخته‌شده از آن، چیز اشتباهی را آزمایش می‌کند.

**چرا تست رگرسیون سه چیز را بررسی می‌کند؟** اگر فقط «روی patched کرش نمی‌کند» بررسی
می‌شد، وصله‌ای که برنامه را پیش از رسیدن به parser خارج کند هم قبول می‌شد. بررسی سوم
(انطباق با Oracle) جلوی آن را می‌گیرد.

**چرا یافتهٔ `flaky` تست تولید نمی‌کند؟** تست ناپایدار از نبود تست بدتر است.

**چرا CI کد خروج را دور نمی‌ریزد؟** هیچ `|| true` در مرحلهٔ تصمیم نیست. گزارش‌ها با
`if: always()` آپلود می‌شوند ولی مرحلهٔ ارزیابی کد خروج، شکست را شکست نگه می‌دارد.

### یافتهٔ واقعی برای تحلیل

دو نتیجهٔ کوچک‌سازی را مقایسه کن و تفاوت را توضیح بده:

| ورودی | نتیجه |
|-------|-------|
| `boundary_text32` (۴۰ بایت) | کاهش **۰٪** |
| `vuln_text_long` (۲۰۸ بایت) | کاهش **۶۴.۹٪** به ۷۳ بایت |

پاسخ: در دومی، ddmin بایت *طول* را حذف کرد و در نتیجه یک بایت payload به‌عنوان طول
تفسیر شد — ورودی کوچک‌تری که به همان خطا می‌رسد. در اولی، هر حذفی ساختار را می‌شکند و
خطا از بین می‌رود، پس ورودی از قبل کمینه است. **۰٪ یک شکست نیست، یک اندازه‌گیری است.**

### تمرین تغییر محدود

> **تعداد بازپخش را از ۳ به ۵ افزایش بده** (`reproduction.replays` در YAML).

- انتظار: schema حداقل ۳ را الزامی می‌کند، پس ۵ پذیرفته می‌شود ولی ۲ نه.
- **آزمایش:** `patch-validator validate --config ...` و سپس بررسی
  `report.json → reproductions[].replay_count == 5`. همچنین `reproduction: {replays: 2}`
  باید با کد ۳۰ رد شود.

> **جایگزین:** یک فیلد جدید به بستهٔ بازتولید اضافه کن (مثلاً مدت زمان هر بازپخش به
> تفکیک) و آن را در `REPRODUCE.md` چاپ کن. آزمایش:
> `pytest tests/test_end_to_end.py -k bundles`.

## تقسیم کار و ثبت مشارکت واقعی

سند تأکید می‌کند تقسیم بالا **پیشنهادی** است و مسئولیت واقعی هر فرد باید مطابق مشارکت
واقعی ثبت شود، و تعداد خطوط یا کامیت‌ها به‌تنهایی ملاک نیست.

پیشنهاد عملی برای ثبت قابل‌دفاع:

1. هر عضو commitهای خودش را با نام خودش بزند.
2. برای هر ماژول، نام مسئول در بالای فایل یا در جدول زیر ثبت شود.
3. هر عضو یک «یافتهٔ واقعی» از اجرای ابزار انتخاب کند و تحلیل آن را خودش بنویسد.

| config, build, vcs, cli | — | |
| execution, sandbox, crash | — | |
| diffparse, cfunctions, patch, differential, classify | — | |
| minimize, reproducer, regression, report, CI | — | |

## پرسش‌های محتمل و پاسخ‌های کوتاه

**اگر مدرس یک وصلهٔ ناشناخته بدهد، ابزار چه می‌کند؟**
```bash
patch-validator validate --config configs/recparse.yaml --patched-revision <new-branch>
```
هیچ‌چیز در پیکربندی یا کد به نام وصله یا شناسهٔ آن وابسته نیست. تست
`test_no_decision_depends_on_the_patch_identity` این را ساختاری بررسی می‌کند: هیچ فیلدی
در ورودی موتور طبقه‌بندی نام revision یا وصله ندارد.

**اگر وصله فایل جدیدی اضافه کند چه؟**
`diffparse` وضعیت `added` را تشخیص می‌دهد؛ خطایی در آن فایل روی نسخهٔ patched به‌عنوان
تغییر سمت جدید تطبیق داده می‌شود.

**چرا exit code ۴۰ بالاتر از ۰ است ولی پایین‌تر از ۲۰؟**
ترتیب از سند رسمی می‌آید: `30 > 10 > 20 > 40 > 0`. سند راهنمای پیاده‌سازی ترتیب دیگری
گفته بود؛ طبق «قانون صفر» سند رسمی مرجع است. این تعارض در
`docs/REQUIREMENTS.md § C-01` و `ADR-004` ثبت شده.

**اگر symbolization نباشد چه اتفاقی می‌افتد؟**
`signature_quality` برابر `unsymbolized` می‌شود و همبستگی از `WEAK` فراتر نمی‌رود. یافته
حذف نمی‌شود، ولی به وصله نسبت داده نمی‌شود.

**چرا از Docker برای هر تست استفاده نشد؟**
اصلاحیهٔ معماری سند صریحاً خلافش را می‌خواهد: یک container به ازای هر CI job، یک sandbox
سبک به ازای هر تست. ساخت container برای هر تست ده‌ها برابر کندتر است و نیازمند دسترسی
به daemon — یک سطح دسترسی خطرناک داخل CI.

**اگر برنامهٔ هدف چند ثانیه طول بکشد و timeout بخورد چه؟**
`timeout` به‌عنوان آسیب‌پذیری طبقه‌بندی **نمی‌شود**. در محور کامل‌بودن تحلیل ثبت می‌گردد
و باعث `INCONCLUSIVE` می‌شود، نه `VULN_REMAINS`.
