# REGRESSION TESTING

از یک خطای مشاهده‌شده تا یک تست خودکار که در اجراهای بعدی آن را می‌گیرد.

## زنجیرهٔ کامل

```
خطای مشاهده‌شده روی base
   │
   ├─► کوچک‌سازی ورودی (ddmin)        ← predicate: همان امضای خطا
   │
   ├─► بستهٔ بازتولید                  ← ≥۳ بازپخش، تعیین پایداری
   │
   └─► تست رگرسیون تولیدشده           ← فقط اگر یافته پایدار باشد
```

هر مرحله می‌تواند متوقف شود و دلیلش ثبت می‌گردد. یافتهٔ ناپایدار هرگز به تست تبدیل
نمی‌شود، چون تست flaky از نبود تست بدتر است.

---

## ۱. کوچک‌سازی ورودی

### معیار حفظ خطا

سند صریح است: **«هر کد خروج غیرصفر را به‌عنوان حفظ خطای اصلی نپذیر.»**

predicate ما:

> اجرای ورودی کوچک‌شده روی **همان باینری** باید **همان `crash_signature`** را تولید کند.

امضا شامل نوع خطا، مکانیزم تشخیص، و سه فریم بالایی هدف **به‌همراه شمارهٔ خط** است. پس
ورودی کوچک‌تری که در تابع دیگری کرش کند رد می‌شود — آن یک باگ دیگر است، و تست رگرسیونی
که از آن ساخته شود چیز اشتباهی را آزمایش می‌کند.

### الگوریتم

`ddmin` بایت‌محور، مستقل از فرمت:

```
granularity = 2
تا وقتی ورودی ≥ ۲ بایت است:
    ورودی را به n قطعه تقسیم کن
    برای هر قطعه:
        candidate = ورودی بدون آن قطعه
        اگر predicate(candidate) برقرار بود:
            ورودی = candidate؛ granularity را کم کن؛ از اول
    اگر هیچ قطعه‌ای حذف نشد:
        granularity را دو برابر کن
```

- نتایج بر اساس **هش محتوا** cache می‌شوند؛ ddmin همان دنباله را زیاد بازدید می‌کند و
  هر miss یک اجرای کامل داخل sandbox است.
- بودجهٔ سخت: `max_iterations` و `budget_seconds`.

### نتایج واقعی

| ورودی | اندازه | کوچک‌شده | کاهش | چرا |
|-------|--------|-----------|------|-----|
| `vuln_text_long` (recparse) | ۲۰۸ B | ۷۳ B | **۶۴.۹٪** | ddmin بایت *طول* را حذف کرد، پس یک بایت payload به‌عنوان طول تفسیر شد — ورودی کوچک‌تری که به همان خطا می‌رسد |
| `boundary_text32` (recparse) | ۴۰ B | ۴۰ B | **۰٪** | هر حذفی ساختار رکورد را می‌شکند و خطا از بین می‌رود |
| `security_object_truncated_after_comma` (cjson) | ۷ B | ۶ B | **۱۴.۳٪** | `{"a":1,` → `{"":1,` — نام کلید حذف شد |

**۰٪ یک شکست نیست، یک اندازه‌گیری است.** گزارش می‌نویسد: «no byte could be removed
without changing the fault; the input is already minimal with respect to this
predicate».

وقتی بودجه تمام شود، گزارش می‌نویسد نتیجه «کوچک‌ترین ورودی یافت‌شده در بودجه است، نه
کمینهٔ اثبات‌شده».

### ردّ تلاش‌ها

هر تلاش در `minimized/<finding>/trace.json` ثبت می‌شود: شمارهٔ تکرار، اندازهٔ کاندیدا،
granularity، پذیرفته شد یا نه، و اینکه از cache آمد یا اجرا شد.

## ۲. بستهٔ بازتولید

### محتوا

```
bundles/<finding>/
  manifest.json      همهٔ فراداده
  input.bin          ورودی اصلی
  minimized.bin      ورودی کوچک‌شده (اگر کوچک‌تر شده باشد)
  crash.txt          گزارش خطا + stack trace کامل
  REPRODUCE.md       دستورالعمل انسانی
  replays/0,1,2/     stdout، stderr و فرادادهٔ هر بازپخش
```

`manifest.json` شامل: هدف و دو revision، هش کامل commit، حالت build، کامپایلر و
نسخه‌اش، `cflags`/`ldflags`، دستورهای ساخت، مسیر و **SHA256** باینری، روش ورودی و
قالب argv، هش و اندازهٔ هر دو ورودی، نتیجهٔ کوچک‌سازی، متغیرهای محیطی، timeout و
محدودیت منابع، backend و پیکربندی sandbox، گزارش کامل خطا، نتیجهٔ هر بازپخش، و
شناسهٔ محیط اجرا (پلتفرم، کرنل، نسخهٔ ابزارها، digest ایمیج container).

### پایداری

هر یافته **حداقل سه بار** بازپخش می‌شود و نتیجهٔ هر اجرا **جداگانه** ثبت می‌گردد.

| وضعیت | شرط | پیامد |
|--------|------|--------|
| `stable` | همهٔ بازپخش‌ها امضای ثبت‌شده را تولید کردند | تست رگرسیون تولید می‌شود |
| `flaky` | بعضی بله، بعضی نه | **تست تولید نمی‌شود**، بررسی الزامی رد می‌شود |
| `not_reproduced` | هیچ‌کدام | مشاهدهٔ اصلی تأیید نشد |

یافتهٔ `flaky` بررسی الزامی `findings_reproducible` را رد می‌کند، یعنی اجرا هرگز
`COMPLETE` گزارش نمی‌شود. نرخ موفقیت میانگین گرفته نمی‌شود — «۲ از ۳» پایدار نیست.

### بازپخش از خط فرمان

```bash
patch-validator reproduce runs/<id>/bundles/<finding>/
```

باینری ثبت‌شده را پیدا می‌کند، **SHA256 آن را تأیید می‌کند**، و اگر نخواند یا باینری
نباشد با کد ۳۰ خارج می‌شود و دستورهای ساخت لازم را چاپ می‌کند — به‌جای گزارش موفقیت
دروغین روی باینری اشتباه.

## ۳. تولید تست رگرسیون

### سه assertion، نه یکی

```yaml
expectations:
  base:
    must_fault: true
    error_type: STACK_BUFFER_OVERFLOW
    location_signature: 9282e270...
    location: src/record.c:22
  patched:
    must_fault: false
    oracle:
      exit_code: 2
      stderr: {match: contains, value: "too long"}
```

| # | بررسی | چرا لازم است |
|---|-------|---------------|
| ۱ | خطا روی base **رخ می‌دهد** | اگر روی base هم خطا ندهد، تست دیگر چیزی را محافظت نمی‌کند |
| ۲ | همان خطا روی patched **رخ نمی‌دهد** | هدف اصلی تست رگرسیون |
| ۳ | patched با **Oracle** می‌خواند | بدون این، وصله‌ای که برنامه را پیش از رسیدن به parser خارج کند هم قبول می‌شد |

بررسی سوم مهم‌ترین است و الزام «صرفاً به Exit Code تکیه نکن» را برآورده می‌کند.

### Oracle از کجا می‌آید

از **test case اصلی** که یافته از آن آمده، یعنی از مشخصات هدف. تولید تست هرگز رفتار
نسخهٔ وصله‌شده را به یک انتظار تبدیل نمی‌کند؛ این دقیقاً همان چیزی است که Oracle مستقل
را بی‌معنا می‌کرد.

اگر test case اصلی Oracle نداشته باشد، تست تولید می‌شود ولی با یادداشت صریح که فقط
می‌تواند وجود و نبود خطا را بررسی کند.

### خروجی

```
regression/<id>/
  input.bin           ورودی کوچک‌شده
  testcase.yaml       قطعهٔ آمادهٔ ادغام در پیکربندی هدف
  expectations.json   سه انتظار بالا
  README.md           توضیح اینکه از چه چیزی محافظت می‌کند
regression/suite.json مجموعهٔ همهٔ تست‌های تولیدشده
```

`testcase.yaml` را می‌توان مستقیماً در بخش `tests` پیکربندی هدف قرار داد؛ از آن پس در
ماتریس عادی اجرا می‌شود و در هر اجرای بعدی CI بررسی می‌گردد.

### حذف تکراری

یک مکان خطا یک بار پردازش می‌شود. چند ورودی معمولاً به یک نقص می‌رسند و تولید بسته به
ازای هر ورودی فقط تعداد اجراهای sandbox را چند برابر می‌کند بدون آنکه شاهد تازه‌ای
اضافه کند. کلید حذف تکراری `location_signature` است.

نمونهٔ واقعی از `recparse`: چهار ورودی خطاساز به سه مکان متمایز می‌رسند
(TEXT سانیتایزشده، RAW سانیتایزشده، fortify در release)، پس سه بسته ساخته می‌شود نه
چهار.
