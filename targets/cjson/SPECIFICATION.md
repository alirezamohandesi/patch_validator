# cjson_cli — Functional Specification (Independent Oracle)

> **مرجع مستقل صحت رفتار برای هدف واقعی.** مطابق `R-ORC-01/02` و `ADR-006`، این سند از
> دو منبع مستقل استخراج شده و **هیچ بخشی از آن از اجرای نسخهٔ وصله‌شده به دست نیامده است**:
>
> 1. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) — گرامر JSON
> 2. مستندات رسمی cJSON (`README.md` بالادست) — قرارداد توابع `cJSON_ParseWithLength`،
>    `cJSON_PrintUnformatted` و `cJSON_Delete`
>
> صحت استخراج به‌صورت مستقل بررسی شد: شکل متعارف خروجی برای ۱۱ ورودی معتبر **ابتدا از
> روی گرامر نوشته شد** و سپس با رفتار کتابخانه مقایسه گردید؛ هر ۱۱ مورد منطبق بودند.

## 1. Why this target

`recparse` را خودمان نوشته‌ایم، پس نمی‌تواند قابلیت تعمیم ابزار را اثبات کند. این هدف یک
کتابخانهٔ واقعی و پرکاربرد است با یک **آسیب‌پذیری حافظه‌ای واقعی و commit رفع واقعی** در
تاریخچهٔ بالادست:

| | |
|---|---|
| پروژه | [cJSON](https://github.com/DaveGamble/cJSON) |
| نوع نقص | heap buffer over-read در `parse_object()` |
| گزارش بالادست | issue #800 |
| commit رفع | `3ef4e4e730e5efd381be612df41e1ff3f5bb3c32` — «Fix heap buffer overflow» |
| نسخهٔ پایه | `826cd6f842ae7e46ee38bbc097f9a34f2947388d` (والد commit رفع) |
| اندازهٔ وصله | ۵ خط افزوده در یک تابع |

وصله یک بررسی `cannot_access_at_index(input_buffer, 1)` بلافاصله پس از پردازش ویرگول
جداکنندهٔ اعضای شیء اضافه می‌کند. بدون آن، وقتی ورودی دقیقاً پس از یک ویرگول تمام می‌شود،
تجزیه‌گر بایت بعدی را می‌خواند که **خارج از بافر** است.

## 2. The harness

cJSON یک کتابخانه است و خودش برنامهٔ اجرایی ندارد، اما الزام `SPEC §2` هدفی می‌خواهد که
ورودی را از فایل/stdin/argv بگیرد. `targets/cjson/harness/cjson_cli.c` این رابط را فراهم
می‌کند و **هیچ منطق تجزیه‌ای ندارد**؛ هر تصمیمی که گزارش می‌کند از کتابخانهٔ تحت آزمون
می‌آید. harness در هر دو نسخه یکسان است و خارج از مخزن هدف نگهداری می‌شود، بنابراین تنها
متغیر میان دو build، خود کد cJSON است.

دو تصمیم در harness عمدی‌اند:

1. بافر ورودی **دقیقاً به اندازهٔ ورودی** تخصیص می‌یابد و `NUL`-terminated نیست، و از
   `cJSON_ParseWithLength()` استفاده می‌شود. این همان API مستند برای تجزیهٔ بافر کران‌دار
   است و تنها راهی است که خواندن فراتر از انتهای بافر اصلاً **قابل مشاهده** شود؛ با بافر
   `NUL`-terminated، آن بایت نگهبان نقص را پنهان می‌کند.
2. خروجی با `cJSON_PrintUnformatted()` تولید می‌شود که قالب آن مستند و پایدار است
   (فشرده، بدون فاصلهٔ غیرضروری، با حفظ ترتیب کلیدها)، پس شکل متعارف خروجی از روی گرامر
   قابل استخراج است.

## 3. Invocation

```
cjson_cli            # ورودی از stdin
cjson_cli -          # ورودی از stdin (صریح)
cjson_cli FILE       # ورودی از FILE
```

## 4. Behaviour

| شرط | خروجی استاندارد | کد خروج |
|------|------------------|---------|
| ورودی یک مقدار JSON معتبر در ابتدای بافر است | شکل متعارف فشردهٔ آن مقدار، به‌علاوهٔ `\n` | `0` |
| ورودی مقدار JSON معتبری در ابتدا ندارد | — | `1` |
| خواندن ورودی یا تولید خروجی ناموفق | — | `2` |
| تعداد آرگومان نادرست | — | `64` |

پیام‌های خطا روی stderr نوشته می‌شوند؛ متن دقیق بخشی از قرارداد نیست، فقط زیررشتهٔ
`invalid json` برای ورودی نامعتبر تضمین می‌شود.

### 4.1 شکل متعارف خروجی

خروجی، سریال‌سازی فشردهٔ مقدار تجزیه‌شده است: بدون فاصله یا خط جدید اضافی، رشته‌ها با
گیومهٔ دوتایی، اعداد صحیح بدون صفر یا علامت اضافی، و کلیدهای شیء به ترتیب ورودی. برای
مجموعه آزمون این پروژه عمداً از اعداد اعشاری، نماد نمایی و دنباله‌های گریز یونیکد پرهیز
شده است، چون شکل متعارف آن‌ها در گرامر یکتا نیست و اتکا به رفتار یک پیاده‌سازی خاص،
استقلال Oracle را از بین می‌برد.

### 4.2 بایت‌های اضافی پس از مقدار

> این بند مهم‌ترین نکتهٔ استخراج Oracle برای این هدف است.

`cJSON_ParseWithLength` طبق مستندات بالادست یک مقدار را از **ابتدای** بافر می‌خواند و
مصرف کامل بافر را الزامی نمی‌کند؛ برای آن رفتار تابع جداگانهٔ `cJSON_ParseWithLengthOpts`
با پرچم `require_null_terminated` وجود دارد. بنابراین ورودی `{"a":1}x` برای این نقطهٔ
ورود **خطا نیست** و باید `{"a":1}` با کد خروج `0` تولید کند.

این با سخت‌گیری RFC 8259 — که `{"a":1}x` را یک متن JSON معتبر نمی‌داند — تفاوت دارد.
Oracle عمداً **قرارداد مستند خودِ تابعی که فراخوانی می‌شود** را دنبال می‌کند، نه تفسیر
سخت‌گیرانه‌تر RFC را؛ در غیر این صورت ابزار یک انحراف را به هر دو نسخه نسبت می‌داد و
یافته‌ای تولید می‌کرد که ربطی به وصله ندارد. این انحراف اینجا صریحاً ثبت شده است.

## 5. Memory-safety requirements

1. هیچ ورودی — معتبر، مرزی یا نامعتبر — نباید موجب خواندن یا نوشتن خارج از محدودهٔ بافر
   ورودی شود. این شامل ورودی‌هایی است که **در میانهٔ یک ساختار تمام می‌شوند**.
2. تجزیه‌گر پیش از خواندن هر بایت باید در دسترس بودن آن را در محدودهٔ طول اعلام‌شده بررسی
   کند؛ اتکا به وجود پایان‌دهندهٔ `NUL` مجاز نیست، چون `cJSON_ParseWithLength` بافر
   بدون پایان‌دهنده را می‌پذیرد.
3. برنامه در هیچ شرایطی نباید با سیگنال خاتمه یابد.

## 7. Known-vulnerable baseline

نسخهٔ پایه بند ۵ را نقض می‌کند: در `parse_object()` پس از مصرف ویرگول، بدون بررسی دسترسی
به بایت بعدی، `offset` یک واحد جلو می‌رود و سپس مقدار بعدی خوانده می‌شود. برای ورودی‌ای
که دقیقاً پس از ویرگول تمام می‌شود، این خواندن از انتهای بافر عبور می‌کند و
AddressSanitizer آن را به‌عنوان `heap-buffer-overflow` گزارش می‌کند.
